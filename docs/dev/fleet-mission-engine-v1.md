## Existing chain and disposition

Today: production order -> free orbital stock -> homogeneous stationed group -> reserved group plus planned transfer -> relocated stationed group. Cancellation releases the reserved group at its current planet immediately. Ships remain in the group throughout the transfer; transfer rows do not hold a second inventory.

## Decided authority for Block 51

The following are implementation contracts, not descriptions of code already delivered. Proposed `D/Fleets/FleetMission.cs` is the single aggregate for an outbound journey and any return leg. It owns civilization, immutable journey endpoints, type, phase, server UTC deadlines, recall intent/result and composition/cargo children. A return is never a second mission competing for the same ships.

1. **Ship ownership:** free OrbitalAssetStock, stationed OrbitalGroup and active mission composition are mutually exclusive accounting locations. Launch removes selected quantities from their source in the same transaction that creates positive, unique mission/type rows (C/O/P). Historical composition snapshots are nonspendable. Do not count a reserved legacy group and imported mission composition twice.
2. **Stationary representation:** new deploy/return settlement credits free OrbitalAssetStock exactly once. Existing groups remain homogeneous stationary organization, allocated from free stock. BM supplies the shared group-to-mission adapter for partial/full selection; consumed source quantities cease being spendable, with source/provenance recorded before retirement. Do not create zero-quantity groups or credit both stock and groups. CurrentPlanetId is location, group OriginPlanetId remains provenance; a new mission's origin is its actual launch planet.
3. **Cargo/accounting:** mission-owned typed cargo (D) is the only in-flight resource ledger. O/Q debit origin stockpile once for cargo and fuel; T/AB transfer explicit accepted amounts, retaining undelivered balance. ResourceSpend/stock adapters participate in one outer unit of work; no independent auto-committed debit or parallel cargo inventory.
4. **Lifecycle:** B defines legal transitions; Preparing/reserved, Outbound, Processing, Returning and unresolved recovery all remain active while holding assets. Recalled is intent/outcome, not permission to free inventory/slots before return. Completed/settled cancellation or failure alone enters terminal history. Central predicates serve slots, queries, events and UI.
5. **Materialization:** proposed `I/Fleets/FleetMissionArrivalService.cs` (R) is the single claim/dispatch entrypoint for due mission legs. S/T/X/V are outcome handlers; U evolves into the shared `FleetMissionReturnService` handler in AB, called under the same claim/transaction. They are not separately scheduled processors. AC refresh and AD worker both invoke this authority.
6. **Recall:** AA coordinates a conditional domain transition on the same aggregate/version used by arrival; it never releases a group or credits stock directly. AB performs actual timed return settlement. API retries return the persisted result and cannot restart a return timer.
7. **Time:** inject one server UTC clock through command/refresh orchestration. Persist calculation inputs/version and all leg timestamps; ignore client-requested gameplay times. Derive normal return departure from the persisted outbound deadline, not a late worker's wakeup. Bounded catch-up may settle overdue legs once each. Normalize SQL Server datetime2 values at the persistence boundary and serialize explicit UTC; UI only renders deadlines.

Conservation checks (BN/BO/CG) count each ship exactly once across free stock + stationed groups + unsettled missions; only production and documented successful colony-ship consumption change that total. Resources across stockpiles + undelivered mission cargo reconcile with explicit production, spends/fuel and delivered transfers. Stored history, event snapshots and preview projections never contribute balances.

## Transactions, authorization and delivery boundaries

Launch (O) must atomically claim a civilization-scoped idempotency key plus canonical payload, authorize/recheck ownership and visibility, arbitrate slots, debit ships/resources and persist mission/composition/cargo. Same key/same payload returns the existing mission; different payload conflicts. All reads needed for correctness must be protected or rechecked inside the transaction. A preliminary availability query is not a reservation.

P/Q/R/AA use database conditional transitions/version checks plus transactions; BH supplies unique keys, positive-quantity checks and indexes. Serialize per-civilization slot/colony decisions and per-planet stock/resource writers in a consistent order, including production/refresh. The construction/research claim patterns in `I/Buildings/ConstructionOrderCompletionService.cs` and `I/Research/ResearchOrderCompletionService.cs` are precedents, not proof that fleet or shipyard paths already have them. In-process locks and InMemory tests cannot establish multi-process safety.

Arrival and recall compete through the same expected phase/version. Only the committed winner performs effects; a loser reloads and returns the persisted outcome. Claim, destination credit/ownership/bootstrap, return scheduling and transition/event are one transaction; retry after failure cannot leave a claimed-but-undelivered mission. Use uniqueness for per-mission/leg effects where needed. Transient failures roll back; invalid persistent state retains assets and records recoverable diagnostics without inventing settlement.

AI-AM authorize claims -> profile -> civilization -> selected/origin ownership **before** gameplay refresh or mutation. Ignore caller civilization as authority, reject mismatched planet/mission IDs without leaking foreign details, and use MapVisibilityService/knowledge projections for destination lists and previews. Revalidate visibility/ownership at launch. A worker is an internal global caller; player refresh is scoped to the authorized civilization, with bounded relevant work rather than a global scan from a planet-filtered GET.

AC/BP integrate due missions into existing refresh without cloning economy/queue calculations. Coordinate stockpile accrual and delivery through existing economy boundaries before computing headroom; bounded batches must report persisted progress and avoid starvation. AE/AF/BQ project active and terminal history separately with stable ordering/pagination. Events BC/BD are committed consequences, not another state machine. Server reads expose snapshot UTC, phase/deadline, capacity/eligibility and explicit errors; frontend AN-AZ/BA-BB renders/refetches them.

## Legacy cutover and persistence boundary

Choose **safe deprecation with a gated drain**, not automatic conversion: keep current Block 54 behavior while the new engine is incomplete/disabled. BL gates legacy launches, drains existing active OrbitalTransfer rows using their existing reserved-group semantics, and verifies zero unresolved active rows before switching authority. Preserve terminal legacy IDs, timestamps/costs and history read-only. Invalid reserved rows require explicit reconciliation; do not release, duplicate or discard ships to force activation.

The activation gate covers launch, cancel, read-triggered completion, operator routes and worker registration together. After switching, old compatible commands delegate to mission services or return an explicit unsupported result; no old cancellation can bypass timed recall, and no old processor handles a mission-owned ship. Preserve functional stock/group/UI flows through BM/adapters. Do not expose earlier O/AI implementations as a second launch engine while BL/BM are pending; integration tests may use isolated fixtures. V applies the same single-owner rule to ship-backed exploration effects.

BL/BM test preexisting stationary/reserved/terminal rows and repeated activation. No live legacy row inventory or migration was attempted in A. If draining cannot finish, activation stays blocked pending documented manual recovery; automatic import/recalculation is outside this choice. Rollback before activation keeps legacy behavior; after new missions exist, do not re-enable legacy mutations against them. Operator recovery/rollback must preserve the one-holder ledger and have explicit reviewed steps (CT/CU/BX).
